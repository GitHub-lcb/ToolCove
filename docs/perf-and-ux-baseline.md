# 性能与 UI/UX 基线

日期：2026-09-20 · 关联：`e2e/specs/20-performance.spec.js`、`e2e/specs/21-ux.spec.js`、`e2e/specs/22-locale.spec.js`

这份文档记录**实测数字**与**为什么这么改**。它不是愿望清单，而是「防回退锁」的说明——
每条结论都有对应的 E2E 断言，改动让数字变差时会直接红。

## 一、首屏成本（本地静态服务器，3 次取中位数）

| 指标 | 优化前 | 现在 | 说明 |
|---|---|---|---|
| 入口 chunk | 552 KB（gzip 194） | **438 KB（gzip 154）** | 两份语言包原本都在入口里 |
| 启动阶段脚本总量 | 989 KB | **875 KB** | 含首屏期间动态加载的 chunk |
| FCP | 1308 ms | **732 ms** | 同机同页面，噪声较大但方向一致 |
| CLS | 0 | **0** | 布局稳定 |
| 长任务最长 | 107 ms | **< 100 ms** | 无 >50ms 的卡顿级任务 |

### 做了什么

1. **语言包按需加载**：`i18n/index.js` 只静态打包 zh-CN，en-US 走动态 import。
   两份字典合计 231 KB、占入口 41.9%，而任何人只需要一份。
2. **预热时机**（踩了两次坑，都留在代码注释里）：
   - 放 mount 之前排期 → 被算进首屏字节（省下的 116 KB 又付回去）；
   - 用 `requestIdleCallback` 从 0 等空闲 → 启动那一刻就可能空闲，仍在首屏内；
   - 最终：挂载后延迟 1.5s，慢网络（2g）跳过。

### 尚未做（下一批的候选）

- **工具实现仍在首屏**：`agent/tools.js` 在模块加载时构建全部 24 个工具，
  把 luxon(175KB)、js-yaml(58KB)、hash-wasm(55KB) 等拖进启动阶段。
  要修得把「工具元数据」与「execute 实现」拆开（元数据供 `AGENT_TOOL_NAMES` 与能力面板同步使用），
  属于中等重构，收益约 300 KB + 少 4 个请求。
- **语言包字典本身还是格式化的**：压成一行可再省约 43 KB（原始 274 → 231 KB）。

## 二、UI/UX：对比度与键盘可达

`e2e/specs/21-ux.spec.js` 做的是**通用审计**而不是逐元素断言（DOM 猜测太脆，本项目已踩过两次）：
遍历可见叶子文本、解析计算样式、按 WCAG AA 计算对比度；焦点可见性则对前若干个可交互元素逐个检查
outline / box-shadow / border 三者是否至少有一个可见。

### 抓到的真实问题（全部已修）

| 位置 | 问题 | 修法 |
|---|---|---|
| 浅色 `--faint` | `#afb8c4` 在白底 **2.0:1**，却用在行号/时间戳/计数/提示等可读文本上（30 处） | 改 `#626a75`（card 与 well 两种底色都过 AA） |
| 深色 `--faint` | `#3d444d` 在卡片上 **1.76:1**，等于看不见 | 改 `#9aa4b2` |
| 深色主按钮 | 白字压 `#4493f8` 只有 **3.1:1**（按钮文字 12–13px，够不上大字号豁免） | `--primary` 压深到 `#2b6ad0`（5.15:1） |
| 深色 chip / 链接 / 激活态 | 主色压深后这些**文字**跟着变暗（3.67–4.13:1） | 文字类改用更亮的档：`--primary-bright` / `--primary-light` / `--primary-hover: #58a6ff` |
| 深色快捷键提示 | 在 `rgba(255,255,255,.06)` 底上 4.43:1，差一点点 | 换 `--faint` |

修完两套主题的正文对比度**0 处不达标**。

## 三、测量方法上的教训（比数字更重要）

这几条都是**量错**之后才写下来的，避免下次再得出假结论：

1. **不要用 Playwright 的 `locator.click()` 计交互耗时**：它自带可操作性检查、滚动与稳定等待，
   第一版因此量出「切模块中位 1254ms」——那是测试框架的耗时。改成页面内 `dispatch → rAF → rAF`。
2. **交互延迟要测两轮**：首轮混着模块编译与 JIT，会出现 38ms 与 904ms 两种极端；
   用户感知的是「第二次点同一个地方」的开销，所以基线取预热后的中位数。
3. **同一个 page 上重复测量会互相污染**：`addInitScript` 与 `on("request")` 会累积，
   后续轮次的数据会被前一轮的时间戳误判（第一版因此得出「阻塞首屏 0KB」）。每次测量开新 context。
4. **判据优先选确定性的**：首屏成本直接读 `index.html` 的静态引用与启动阶段的资源交付量，
   而不是「FCP 之前发起的请求」——后者依赖墙钟窗口，机器一忙就分类错。
5. **测量类用例必须串行**：与功能用例混跑时 FCP 会从 600ms 翻到 1400ms、请求数都数不对。
   现在 `playwright.config.js` 全局 `workers: 1`，并把测量用例排在最后一个 project。
